2  The grammar of graphics

NoteLearning outcomes & Chapter summary

  1. Understand that the advantage of using a high-level visualization syntax is that it allows us to think in terms of the data, rather than focusing on graphical details.

  2. Understand that a grammar of graphics defines grammatical rules that can be used to construct entire visualizations from smaller building blocks, such as geometric marks and aesthetic encodings.

  3. Identify the data-linked canvas, aesthetic encodings, and geometric marks in Altair and ggplot.

2.1 Why bother?

Why do we need to know anything about visualization libraries and their underlying theory, such as the grammar of graphics? While there is a lot we can learn about visualization without coding, the act of implementing visualizations in code can help us understand their underlying principles, which makes the learning experience more interactive and memorable. The grammar of graphics also gives us a powerful theoretical framework to understand and reason about data visualizations.

2.2 Which visualization library should we pick?

We will start by selecting which visualization library to use. To make an informed decision, it is helpful to understand that most visualization libraries can be classified as taking either a high-level declarative approach or a low-level imperative approach to creating visualizations.

Ex-promptExercise 1

To understand the difference between these two approaches, let’s start with an example, using the following small toy dataset:

x y group
float64 float64 str
0 0.2 0.6 a
1 0.6 0.9 a
2 1.2 1.8 b
3 2.4 2.7 b

A helpful way to illustrate the difference between the two approaches to syntax is to imagine that we want to create a chart where we color the points according to their group. Here is pseudocode1 that illustrates this difference:

  • Imperative syntax
  • Declarative syntax
fig = create_figure()
colors = ['blue', 'orange']
for color, group in zip(colors, df['group'].unique()):
    tmp_df = df[df['group'] == group]
    fig.add_chart(tmp_df['x'], tmp_df['y'], label=group, color=color)
chart(
    x='x',
    y='y',
    color='group'
)

Although the same chart is created from both of these pseudocode examples, the syntax looks wildly different. Pause here and try to describe the differences between the two in your own words. Then, click on the hint and solution below to read our explanation of the two approaches.

Actively engaging with exercises like this one can help you remember and understand the information. The key is to activate your brain and try to come up with an answer yourself rather than skipping straight to passively reading the solution.

Ex-hintHint

Does one of the approaches focus more on the data and the other more on the plot-specific details?

Ex-solutionSolution

Based on the syntax of the exercise above, we can say that a declarative approach to visualization lets us express ourselves in terms of the data (color='group'), whereas an imperative approach to visualization focuses more explicitly on plot construction details such as choosing specific colors and then assigning them to groups by looping through the data.

A related way to understand declarative and imperative approaches is to consider the difference between giving an instruction in each:

  • Declarative instruction
  • Imperative instruction

“Color by the column group in the dataframe.”

Focus: Declaring links between data variables (e.g., group) and graphical properties (e.g., color). The rest of the plot details (such as which colors to use) are handled automatically.

“Loop over the dataframe and plot observations in group a in blue and observations in group b in orange.”

Focus: Being explicit with all the details for creating the chart via loops and low-level drawing commands.

In this book, we will learn about declarative visualization tools, since these allow us to code a high-level specification of what we want the visualization to include, rather than coding out the details of how to implement the visualization. Another way to state this would be that high-level libraries let our minds focus on data and relationships, which is the right level of abstraction for a data scientist. Low-level libraries focus more on plot construction details, which is often more appropriate when making a highly customized visualization, data art, or an application with complex plotting logic.

Among declarative visualization libraries, there are still a few different subcategories. In this book, we are going to learn about libraries that implement a so-called “grammar of graphics”, since this framework makes visualizations easy both to create and to reason about.

2.3 What is the grammar of graphics?

There is a plethora of names used to refer to specific types of chart. While referring to charts by name can be convenient in some contexts, it is often confusing. For example, a scatterplot, a dot plot, a strip plot, a bubble plot, and a forest plot all use points to represent data, but what’s the difference between them? Memorizing exactly which chart corresponds to which name is not as important as developing an understanding of the principles that form the foundations for building visualizations. Such an understanding can move us away from just creating charts from known templates to reflecting on what it is we’re trying to communicate and which graphical elements are the most suitable for this task.

The grammar of graphics lets us focus on understanding the common building blocks of all charts and how to combine them according to predictable rules to create bespoke visualizations. It parallels the grammars of natural2 and programming languages, but applies to visual components. While we’re all familiar with how the grammatical rules of natural languages describe how to compose meaningful sentences from words, it might not be as clear what grammatical structures look like in programming languages, so let’s see an example in the following exercise:

Grammatical origins

The idea of a grammar of graphics originates from Leland Wilkinson’s book The Grammar of Graphics.

Ex-promptExercise 2

What do you think the output of the following Python code would be?

1 + 2

As you might have expected, the output is 3 because Python uses the conventional rules of mathematics to add the two numbers together. Almost all programming languages follow this rule. But what does the + operator do if we are trying to add something other than numbers? What do you think the output of the following code would be? Do you think it differs between programming languages?

'one' + 'two'
Ex-hintHint

Adding two numbers gives their sum. Could adding two strings similarly combine their contents, producing a string with all the characters from both?

Ex-solutionSolution

In Python, the + operator performs concatenation when strings are added together, so the returned result would be "onetwo". In contrast, R does not support adding strings with +, so it would raise an error indicating that non-numeric arguments were passed to the + operator.

This example illustrates that the same expression can behave differently under the grammatical rules of different programming languages.

2.4 Learning the grammar of graphics

So what does the grammar of graphics look like? Well, “it depends”. Just like linguistic grammars vary between languages, visualization grammars are implemented differently in different packages. However, there are some core steps which are present in most grammars of graphics:

  1. Create a data-linked canvas: This step creates a background canvas that other graphical components are drawn upon and links it to the relevant dataset.
  2. Encode visual aesthetics: This step defines how data will be mapped to graphical channels (e.g., the column 'group' might be mapped to the color of each mark).
  3. Add geometric marks: This step selects the graphical elements used to represent the data (e.g., points or bars).

As a result of the predictable structure, a grammar of graphics allows you to create an impressive range of visualizations in an intuitive manner and aids in reasoning about these visualizations. It also makes it notably easier to change between different types of plots, as the code syntax follows a predictable structure and only parts of the specification change between charts. In fact, libraries that implement a grammar of graphics often require fewer changes in the code to create different types of visualizations.3

Implementations of the grammar of graphics

You can think of the grammar of graphics as an underlying theory of how to make visualizations. But to actually create a visualization, we need to use a package that implements this theory in code. This book shows several programmatic implementations and lets you choose which package you prefer to learn, while also allowing for quick comparisons between libraries. Before creating a visualization, let’s see how the structure of these implementations is similar to the general structure we described above.



Stellar naming

Altair is built on Vega-Lite, which in turn is built on the JavaScript visualization library Vega. Vega was named after a star and the name “Altair” was picked because it represents another star in the same astronomical pattern.



A nod in the name

The “gg” in ggplot2 is a reference to Wilkinson’s The Grammar of Graphics, which inspired the creation of the ggplot2 library.

  • Altair
  • ggplot

In the Python package Altair, a general representation of the core chart components would look like this:

alt.Chart(data).encode().mark()
  1. alt.Chart(data) creates the data-linked canvas.
  2. encode(...) encodes the visual aesthetics, such as x and y.
  3. mark_*(...) adds geometric marks, such as points or bars.

Note that we wrote the Altair syntax in the same form as in our general grammar of graphics example above to help you see how it maps onto that structure. It is perfectly fine to keep writing this way if you prefer it, but the canonical way to write Altair chart specifications is in the form alt.Chart(data).mark().encode(). We will follow that order from now on since most examples you will see elsewhere follow this syntax.

In the R library ggplot2, a general representation of the core chart components would look like this:

ggplot(data) + aes() + geom()
  1. ggplot(data) creates the data-linked canvas.
  2. aes(...) encodes the visual aesthetics, such as x and y.
  3. geom_*(...) A geom function adds geometric marks, such as points or bars.

Note that we wrote the ggplot syntax in the same form as in our general grammar of graphics example above to help you see how it maps onto that structure. It is perfectly fine to keep writing this way if you prefer it, but the canonical way to write ggplot chart specifications is in the form ggplot(data, aes()) + geom(). We will follow that order from now on since most examples you will see elsewhere follow this syntax.
